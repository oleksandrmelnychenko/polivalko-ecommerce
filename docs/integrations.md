# Poli Valko — інтеграції

Опис зовнішніх систем для передачі (розділ 11 ТЗ): що вже працює, яка заглушка стоїть до отримання
доступів і що зробити, щоб увімкнути справжню інтеграцію. Усі ключі — змінні середовища, див. [operations.md](operations.md).

Спільні механізми для всіх інтеграцій:

- **Outbox.** Зовнішні виклики після оформлення (передача в Navkolo, чеки, повернення, повідомлення) йдуть через
  чергу в тій самій транзакції, що й зміна в БД. Повтори: 1 хв, 5 хв, 15 хв, 1 год, 3 год, 6 год, до 10 спроб.
  Вичерпана операція потрапляє в «Інтеграції → Черга операцій» з кнопкою «Повторити», а відповідальний отримує тривогу.
- **Журнал синхронізацій.** Кожен запуск фонового завдання зберігає підсумок і звіт помилок; у «Інтеграції»
  видно час останнього успіху. Після трьох невдалих запусків поспіль (`Sync:AlertAfterFailures`) — тривога, після
  відновлення — повідомлення «Відновлено».
- **Тривоги.** Канал — той самий, що й для нових замовлень: Telegram (`TELEGRAM_BOT_TOKEN`; чати — у консолі
  «Налаштування → Сповіщення», запасний — `TELEGRAM_CHAT_ID`), без токена — запис у журнал Worker. Окремі події
  (нові замовлення, заявки, збої інтеграцій, оплата скасованого замовлення) вимикаються там само.

## Navkolo (ERP)

Реалізовано клієнт **DNTrade** для модуля [Navkolo.Торгівля](https://navkolo.one/modul-torhivlia/).
Джерела контракту, перевірені 08.11.2026: [інструкція API](https://help.dntrade.com.ua/posts/api),
[Swagger](https://api.dntrade.com.ua/docs/), [JSON OpenAPI](https://api.dntrade.com.ua/docs/swagger.json).
Довідка Navkolo також описує API DNTrade: https://help.navkolo.one/Update/Torgivlya/update-v6-0-9_07-08-25.
Локальне середовище залишається `Stub`; живий акаунт без ключа не перевірено.

### Підключення через консоль

У **Налаштування → Навколо** вставте ключ API, натисніть **Перевірити підключення**, оберіть склад і статус скасування,
увімкніть синхронізацію й збережіть. Перевірка читає лише списки складів і статусів; не змінює облік чи налаштування.
Збереження з увімкненою синхронізацією повторно перевіряє ключ і склад на сервері та запитує свіжий імпорт.
Worker підхоплює зміни на наступному циклі (до 15 секунд, якщо попередня задача не виконується).

Доступ: окреме право `settings.navkolo.manage`; адміністратор має його, менеджер за замовчуванням — ні.
Порожнє поле залишає поточний ключ. Заміна ключа й видалення доступні тут само; для видалення треба вимкнути
синхронізацію. Збережене налаштування має пріоритет над `.env`, зокрема після видалення ключа старий ключ із
середовища не відновлюється. Паралельне редагування захищене перевіркою версії.

Ключ шифрується ASP.NET Data Protection перед записом у `platform.settings`, не повертається API та не потрапляє
в журнал змін. API і Worker використовують ту саму БД та каталог сертифікатів Data Protection (read-only mount).
Фонові задачі й запити читають налаштування без кешу між процесами. Попередня успішна синхронізація не робить
новий ключ чи склад «свіжими»: при зміні налаштувань потрібен новий знімок.

### Початкове підключення через середовище (необов’язково)

1. У Navkolo: **Опції → Інтеграції → API DNTrade**. Увімкнути API, згенерувати токен,
   обрати групу нових клієнтів і зберегти. Для товарів увімкнути синхронізацію з вебсайтом.
2. У приватному `.env` сервера (шаблон `.env.example`, права `600`) задати:

   ```dotenv
   NAVKOLO_MODE=DNTrade
   NAVKOLO_API_KEY=ваш_токен
   NAVKOLO_STORE_ID=
   NAVKOLO_CHANNEL=Poli-Valko
   ```

   Один склад визначиться автоматично. Якщо складів кілька — вказати UUID потрібного складу
   (`/products/stores`). `NAVKOLO_ORDER_STATUS_ID` — необов'язковий початковий статус з `/orders/statuslist`.
   Для native .NET запуску відповідні змінні: `Navkolo__Mode`, `Navkolo__ApiKey`, `Navkolo__StoreId`.
   Ключ потрібен API і Worker, не Next.js; не використовувати `NEXT_PUBLIC_*` і не комітити `.env`.
3. Перезапустити API та Worker. Перевірити журнал синхронізації в консолі; виконати імпорт каталогу/цін.
   Саме Worker запускає планову синхронізацію й відправляє замовлення з outbox.

### Поведінка

- HTTPS `https://api.dntrade.com.ua/`, заголовок `ApiKey`, перенаправлення заборонені,
  заголовок ключа маскується в HTTP-логах, тіла помилок провайдера не журналюються.
- Сторінки товарів по 100 записів, склад і `website_synch=1`; ціна UAH, доступність `balance - booked`.
  Вагові товари відхиляються з поясненням: кошик наразі підтримує цілі одиниці.
- Кожні 5 хвилин завантажуються каталог, ціни й залишки, нові категорії створюються за UUID/назвою;
  існуючі категорії з попереднім зв'язком за назвою переводяться на UUID. Фото/опис/SEO сайту не перезаписуються.
  Товари, відсутні в успішному повному знімку, приховуються. Порожній коректний знімок також означає,
  що немає товарів, дозволених для вебсайту; помилка відповіді не трактується як порожній каталог.
- Ліміт DNTrade: 100 запитів/хвилину. Клієнт розносить запити на 750 мс і обмежено повторює `429`
  з `Retry-After`; інші збої повторюються планувальником/outbox. Для кількох процесів остаточний ліміт забезпечує провайдер.
- `orders/upload`: UUID замовлення сайту передається в `id`, номер `PV-…` у `private_id`.
  Згідно з контрактом API повторний `id` оновлює існуюче замовлення, а не створює нове.
- Скасування з консолі потрапляє в outbox у тій самій транзакції, що й статус замовлення. Worker викликає
  `orders/setstatus` з UUID замовлення та обраним у консолі статусом із `orders/statuslist`, а потім підтверджує
  результат через `orders/list`. Помилка/втрата відповіді — повтори й журнал; після вичерпання спроб — ручний повтор.
  Статус не вгадується за назвою або числовим ID: його потрібно обрати для свого обліку.
- До першої спроби експорту скасування звільняє локальний резерв одразу, а пізня подія експорту вже не створює
  замовлення в ERP. Початок спроби експорту фіксується до HTTP-запиту. Після початку спроби або успішної передачі
  резерв утримується до підтвердження скасування. Невідомий результат експорту й відсутність запису в ERP не
  прирівнюються до успіху: залишається повторна звірка. Експорт і скасування серіалізуються для одного UUID
  між Worker-процесами. Повторна обробка не звільняє резерв вдруге.
- Якщо DNTrade повідомляє `load=1`, автоматичне скасування через `setstatus` не виконується: потрібне оформлення повернення.
  Уже спожитий/звірений резерв не повертає одиниці на продаж. Повернення коштів не є поверненням товару.
- Історичні скасування до цієї зміни не відправляються масово; картка замовлення явно показує відсутність запиту.
- Резерв належить сайту; `reserve=0` у DNTrade запобігає другому резерву тих самих одиниць.
  Сайт віднімає власні резерви від залишку ERP вже за вирахуванням чужих `booked`.
  Це захищає одночасні оформлення **на сайті**, але не є розподіленим блокуванням каси/інших каналів ERP.
- Після підтвердження `load=1` для того самого UUID через `orders/list` і наступного завантаження залишків
  локальний резерв знімається атомарно з імпортом: відвантаження вже враховане ERP. Без такого підтвердження
  списання не вгадується за різницею залишків. Імпорти серіалізовані між процесами.
- Зворотна синхронізація працює в тому самому завданні кожні 5 хвилин (ручний запуск — **Система → Інтеграції → ціни/залишки**).
  `orders/list` читається з пагінацією та фільтром каналу `Poli-Valko`; обробляються лише UUID відомих замовлень,
  для яких сайт уже почав передачу. Інший канал, невідомий UUID або непередане замовлення не змінюються.
  Обраний статус скасування звіряється з актуальним `orders/statuslist`; `load=1` означає відвантаження незалежно від назви статусу.
- Скасування в ERP переводить невідвантажене замовлення в `Cancelled`, звільняє неспожитий резерв і записує
  підтвердження та історію від «Навколо». Зворотний outbox-запит скасування не створюється.
  Відвантаження переводить активне замовлення в `Shipped`; `Completed` та `Cancelled` не відновлюються назад.
  Свіжі залишки мають містити всі товари відвантаження; інакше вся транзакція відкочується, резерв залишається.
- Повторні запуски не дублюють історію/звільнення резерву. Перед застосуванням статус перечитується після
  завершення експорту/скасування того самого UUID. Помилка ERP, неоднозначна пагінація або помилка імпорту
  не залишає частково оновлених статусів. Наявний журнал синхронізацій показує кількість оновлених замовлень і збої.
- API не повертає версію зміни статусу. Підтверджені факти скасування/відвантаження зберігаються окремо та не
  відкочуються відповіддю «нове» чи `load=0`. Скасоване замовлення з пізнім відвантаженням зберігає `Cancelled`,
  але склад і резерв звіряються з фактичним відвантаженням; у картці є попередження про конфлікт і історія.
  Скасування після відвантаження/виконання не повертає товар на продаж. Повернення оформлюється в обліку.
  Оплата та повернення коштів не підміняються статусом ERP: для оплаченого скасування показується нагадування про повернення.
- Якщо ERP недоступна або дані старші за 20 хвилин, замовлення переходить у `AwaitingConfirmation`,
  онлайн-оплата недоступна; локальний резерв зберігається до підтвердженого скасування/виконання.
- Статуси доставки та повернення товару на склад автоматично не записуються:
  документи відвантаження/повернення ведуться в Navkolo. Грошове повернення саме по собі не збільшує залишок.

Контракт перевіряється HTTP-тестами з тестовими відповідями. Перед production потрібен один контрольний цикл
з реальним ключем: правильний склад/ціна, створення й повторна відправка тестового замовлення, скасування в обох напрямках, `load` та залишки після відвантаження.

## Онлайн-оплата

| | |
|---|---|
| Статус | **Тестовий провайдер** (`Payments:Provider=Sandbox`); адаптер **Plata by mono** готовий, вмикається ключем |
| Модуль | `src/Modules/PoliValko.Payments` |

Потік: «Оплатити» на сторінці замовлення → `POST /api/v1/orders/{n}/payments` створює рахунок (або повертає
активний) → сторінка провайдера → повернення на сторінку замовлення, яка чекає підтвердження.

- **Один рахунок на замовлення.** Відкриття рахунку блокує рядок замовлення до відповіді провайдера: друге «Оплатити»
  (інша вкладка, подвійне натискання) чекає й отримує той самий рахунок, а скасування чекає, доки рахунок запишеться,
  і тому анулює його.
- **Після успішної оплати** інші відкриті рахунки замовлення анулюються (як при скасуванні).
- **Зайва оплата.** Якщо замовлення вже оплачене, а провайдер повідомляє про успіх ще одного рахунку, замовлення
  не змінюється, другого чека немає: спроба позначається «Зайва оплата…» у картці замовлення, відповідальний
  отримує тривогу повернути ці кошти в кабінеті провайдера. Коли провайдер повідомить про повернення, позначка
  змінюється на «Зайву оплату повернено». Повернення з картки замовлення йдуть через рахунок, що оплатив замовлення.

- Статус змінює лише **перевірене повідомлення** провайдера (`POST /api/v1/payments/webhooks/{provider}`):
  тестовий — HMAC-SHA256 (`Payments:Sandbox:Secret`), mono — ECDSA `X-Sign` з публічним ключем мерчанта.
- **Дублікати** відсікає унікальний ключ події; **старіші** повідомлення не відкочують стан.
- **Фонова звірка** (`payments.reconcile`, кожні 2 хв) питає статус незавершених оплат: підхоплює втрачені вебхуки
  й прострочені рахунки.
- **Повторне відкриття**: після відмови чи прострочення покупець відкриває нову спробу.
- **Скасування** картково-оплачуваного замовлення анулює його відкриті рахунки (mono: `invoice/remove`): сторінка оплати,
  що лишилася відкритою, більше не приймає гроші. Якщо покупець устиг оплатити раніше, оплата приймається,
  а відповідальний отримує тривогу оформити повернення.
- Розбіжність суми не позначає замовлення оплаченим і викликає тривогу.
- **Сторно провайдера** (`reversed`: повернення в кабінеті мерчанта чи банківське сторно). Якщо його пояснюють
  повернення, оформлені на сайті (виконані або ще в обробці), нічого не змінюється. Інакше:
  - повернуто все, що лишалося: на замовленні записується виконане повернення всіх ще не повернутих позицій
    («Кошти повернуто поза сайтом…»), статус оплати стає «Кошти повернено», видається чек повернення, приходить тривога;
  - повернуто частину: сайт не знає, за які позиції, тому замовлення не змінює, лише надсилає тривогу.

Тестова сторінка `/pay/sandbox/…` дає змогу перевірити успіх, відмову, прострочення й «втрачений вебхук».
Її маршрути існують лише при `Payments:Provider=Sandbox`. Sandbox стартує лише з `Payments:AllowSandbox=true`
(розробка, тести, локальний compose, staging); `deploy/compose.production.yaml` закріплює `false`, тож на production
API й worker із Sandbox не запускаються. Невідоме значення `Payments:Provider` чи `Mono` без токена теж зупиняють старт.

Щоб увімкнути mono: `PAYMENTS_PROVIDER=Mono`, `MONO_TOKEN=<X-Token мерчанта>`, `SITE_URL` — публічна адреса
з HTTPS (на неї приходять вебхуки). Перед запуском пройти тестовий цикл з тестовим мерчантом.

## Повернення коштів

- Менеджер оформлює повне чи часткове повернення **за позиціями** в картці замовлення.
- Оплата карткою: гроші повертає провайдер у фоні; ідентифікатор повернення передається як ключ операції (`extRef`).
  Ключ записується в повернення **до** запиту. Якщо відповідь втрачено (таймаут, збій, перезапуск), повторна обробка
  спершу шукає повернення за ключем у `cancelList` статусу рахунку і надсилає його вдруге, лише якщо mono його не прийняв.
- Відповідь mono `processing` не вважається виконаним поверненням: воно лишається «Видається», а фонова звірка
  (`payments.reconcile`) завершує його, коли mono повідомить `success` чи `failure`. Чек повернення — лише після `success`.
- Одночасні повернення одного замовлення (дві вкладки, два менеджери) виконуються по черзі: друге бачить перше
  й не може повернути ті самі позиції ще раз.
- Тестовий провайдер не зберігає окремих повернень: якщо відповідь втрачено, повернення лишається «Видається»
  і приходить тривога звірити його вручну; вдруге воно не надсилається.
- Оплата під час отримання: повернення відбувається поза сайтом, сайт його фіксує.
- Оплачене замовлення можна скасувати лише після повного повернення.

| Картка онлайн | після підтвердженої оплати (`Fiscal:IssueOn:Card=Payment`) | `CASHLESS` |
| Післяплата | після статусу «Виконане» (`Completion`) | `CASHLESS` |
| У магазині | не видає (`None`), чек дає каса магазину | `CASH` |

Чек повернення — на кожне повернення, якщо сайт видавав чек продажу. Ідентифікатор чека — ключ ідемпотентності:
повтор після збою не створює другого чека. Чеки видно в консолі й покупцю на сторінці замовлення.

Щоб увімкнути Checkbox: `FISCAL_PROVIDER=Checkbox`, `CHECKBOX_LICENSE_KEY`, `CHECKBOX_CASHIER_LOGIN`,
`CHECKBOX_CASHIER_PASSWORD`. Перевірити на тестовій касі всі сценарії з розділу 6 ТЗ. Закриття зміни (Z-звіт)
налаштовується в кабінеті Checkbox.

## Нова пошта

| | |
|---|---|
| Статус | **Демо-довідник** без ключа; з ключем — локальна копія з API 2.0 |
| Модуль | `src/Modules/PoliValko.Delivery` |

- З `NOVAPOSHTA_API_KEY` Worker щоночі (`novaposhta.directory`) завантажує міста (`Address.getCities`) і робочі
  відділення й поштомати (`AddressGeneral.getWarehouses`). Зниклі відділення стають неактивними, а не видаляються.
- Якщо API повернув менше половини поточних відділень, запуск вважається невдалим і нічого не деактивується.
- Пошук міста — за початком назви; без запиту показуються міста з найбільшою кількістю відділень.
- Доставка — за тарифами перевізника; вартість на сайті не рахується (розділ 6 ТЗ).
- Точки самовивозу (адреса, графік, інструкція, посилання на карту) і перемикачі способів доставки редагуються в «Налаштування → Доставка». Самовивіз пропонується, лише коли він увімкнений і є хоча б одна доступна точка.

## Листи покупцям

| | |
|---|---|
| Статус | **Заглушка** (`Email:Mode=Log`): листи не надсилаються, посилання пишуться в журнал API лише в Development |
| Модуль | `src/Modules/PoliValko.Notifications` (контракт `ICustomerMailer`), відправник — `src/Modules/PoliValko.Customers` |

- Кабінет покупця надсилає два листи: підтвердження пошти (посилання діє 3 дні) і скидання пароля (1 година, одноразове).
  Посилання ведуть на `SITE_URL/account/confirm-email?token=…` і `SITE_URL/account/reset-password?token=…`.
- Локально посилання видно в `docker compose logs api` (шукайте `confirm-email` або `reset-password`).
- Щоб підключити справжню пошту: обрати провайдера (SMTP хостингу, SendGrid, Mailgun, eSputnik тощо), написати клас,
  що реалізує `ICustomerMailer`, у `Notifications/Integrations/Email/` і зареєструвати його для нового значення `Email:Mode`.
  Листи надсилаються одразу під час запиту, а не через outbox: токени не повинні зберігатися в черзі.
- **До запуску на production заглушку треба замінити:** у режимі `Log` робочі посилання для входу в чужий акаунт
  потрапляють у журнали сервера.
