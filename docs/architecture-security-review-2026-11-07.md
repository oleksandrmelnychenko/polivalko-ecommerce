# Огляд архітектури й безпеки — 7 листопада 2026

## Межі перевірки

Огляд поточного робочого дерева: межі frontend/backend-модулів, новий 3D-помічник, вибрані шляхи автентифікації й авторизації, CSRF, доступ до замовлень, ідемпотентність, платіжні повідомлення, HTML-контент, медіа та конфігурація розгортання. Це цільовий огляд коду з локальними перевірками, не повний пентест чи підтвердження захищеності production. Реальні платежі й зовнішні облікові записи не використовувалися.

## Висновок щодо архітектури

Модульний моноліт API + Worker зі спільною PostgreSQL та окремими shop/console відповідає поточному масштабу магазину. Потреби розділяти його на мікросервіси в перевірених сценаріях не виявлено. Backend-модулі взаємодіють через Contracts; їхні межі перевіряють architecture-тести. Frontend має фічеві модулі з публічними index.ts/server.ts та ESLint-правилами залежностей.

Помічник інтегрований окремою фічею `assistant`, від якої залежить лише `layout`. Логотип залишається статичним. Three.js завантажується динамічно при монтуванні відкритої панелі; GLB — з фіксованого same-origin шляху. У перевіреному GLB немає зовнішніх URI для буферів або зображень. Код із демонстраційного сервера, чат і голос не перенесені. Закриття скасовує fetch, цикл анімації, підписки та звільняє ресурси сцени. Модель близько 6 МБ: для мобільного трафіку доцільна окрема оптимізація активу зі збереженням анімацій.

## Підтверджений дефект: стан платіжної спроби при розбіжності суми (P2)

Джерело: `src/Modules/PoliValko.Payments/Features/Processing/PaymentProcessor.cs:51–61`.

У гілці Succeeded статус спроби встановлюється в Succeeded **до** перевірки Amount. Якщо сума не збігається, код надсилає IntegrationAlert і зберігає цей статус, але не викликає MarkPaidAsync. Наступна коректна подія Succeeded для тієї самої спроби не проходить умову `payment.Status != Succeeded`, навіть з новим event key та новішим часом. Виникає розбіжність між станом спроби й замовлення, а автоматичне виправлення наступним повідомленням блокується.

Умова: достовірне повідомлення провайдера з відмінною сумою або відповідний результат звірки. Для зовнішнього атакувальника довільний виклик webhook недостатній: перевірка підпису стоїть перед обробкою. Це підтверджений аналізом коду дефект цілісності стану, а не доведена можливість оплатити замовлення меншою сумою. Живим платіжним провайдером сценарій не відтворювався.

Рекомендація: перевіряти суму до переходу в Succeeded; відображати розбіжність окремим станом/ознакою, придатною для звірки. Додати інтеграційний сценарій «невідповідна сума → коректна новіша подія», перевірити статуси обох сутностей і одноразову фіскалізацію. У межах цього огляду платіжний код не змінено.

## Перевірені захисні механізми

- Локальні анонімні GET `/api/v1/console/users`, `/api/v1/console/orders`, `/api/v1/account/orders` повернули 401; користувач Manager отримав 403 на `/api/v1/console/users`.
- Після входу Manager POST `/api/v1/console/auth/logout` без CSRF-токена повернув 400. Переглянуті staff-групи використовують permission-політики й CSRF-фільтр; це не вичерпний перебір усіх маршрутів.
- Гостьове замовлення читається через випадковий токен, який зберігається як хеш; порівняння constant-time. Кабінет перевіряє CustomerId. GET неіснуючого замовлення з неправильним токеном повернув 404; сам по собі цей тест не доводить ізоляцію реальних замовлень різних покупців.
- HTML сторінок і описів товарів проходить allowlist-санітизацію у перевірених шляхах запису й імпорту. Медіасховище обмежує розмір, перевіряє сигнатури дозволених форматів, генерує імена та перевіряє кореневий каталог при видаленні.
- Webhook Mono перевіряє ECDSA-підпис; Sandbox використовує HMAC. Дедуплікація платіжних подій відбувається за provider/event key.
- Підозра на відсутність обробки proxy headers відхилена: `compose.yaml` задає `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true`. Production overlay успадковує її. Наявність прапорця підтверджена кодом конфігурації; Secure-cookie та клієнтський IP через реальний HTTPS Caddy не перевірялися. Поведінка прапорця описана в [документації Microsoft](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/proxy-load-balancer?view=aspnetcore-10.0).

## Потребує окремої перевірки / посилення

1. **Ідемпотентність і власник запиту.** `IdempotencyFilter` включає в scope метод і маршрут, у хеш — route values та body, але не поточного покупця. CreateOrder також використовує customer identity із cookie, отже два різні користувачі з однаковими key/body можуть отримати одну кешовану відповідь із токеном замовлення. Для отримання чужої відповіді потрібні чужий точний ключ і тіло запиту; джерело їх витоку не встановлено, клієнт генерує ключі випадково. Це питання межі ізоляції, не підтверджений віддалений витік. Варто прив'язати авторизовані replay до subject і явно визначити гостьову модель та поведінку після входу.
2. **Ключі Data Protection.** Зберігаються в БД без явно налаштованого ProtectKeys. Компрометація читання БД/резервної копії розкриє ключовий матеріал, тому шифрування ключів окремим від БД ключем посилить ізоляцію. Віддалений шлях доступу до БД не встановлено.
3. **Production-периметр.** Потрібні перевірки реальних HTTPS-cookie, довірених proxy, IP rate limits і доступності консолі. API не має опублікованого порту в перевіреному Compose; дозволяти довільні forwarded headers без мережевої ізоляції не слід. Production overlay вимагає явного вибору платіжного провайдера, але дозволяє Sandbox: перед реальними продажами потрібно перевірити фактичний provider і фіскальний режим.
4. **Майбутній чат/голос.** Запити до моделей мають йти через окремий серверний контракт із лімітами, без секретів у браузері. Доступ до замовлень — через наявні перевірки власника/токена; текст від моделі не може бути дозволом на зміни замовлень чи оплату. Поточна панель цих можливостей не має.

## Виконані перевірки та обмеження

- Shop: TypeScript і ESLint пройшли; ESLint перевіряє дозволені міжфічеві залежності.
- Backend unit/architecture: 108/108 пройшли (`dotnet test --project tests/PoliValko.UnitTests --no-build`, на наявній Debug-збірці; backend-код у цій роботі не змінювався).
- npm production-залежності: `npm audit --omit=dev` — 0 відомих вразливостей на момент запуску. Це перевірка бази advisories, а не гарантія безпеки коду.
- NuGet: `dotnet list PoliValko.slnx package --vulnerable --include-transitive --format json` завершився успішно; для 17 проєктів не повідомлено вразливих пакетів.
- Браузер: 3D відображається на desktop і 390×844; пауза, повторне відкриття, кнопка закриття й Escape працюють; після Escape перевірено відсутність canvas та відкритих dialog, фокус повернувся на кнопку помічника. У зібраному журналі браузера не було помилок JavaScript. Поведінку reduced-motion і fallback проаналізовано в коді, окремого runtime-тесту цього разу не було.
- Повний набір backend integration-тестів не запускався: його fixture потребує Testcontainers, Docker у поточному локальному середовищі був призупинений. Production TLS, зовнішні платежі, SMTP та offsite backup не перевірені.

У перевірених шляхах не встановлено високовпевненої критичної чи високої віддаленої вразливості. Це твердження обмежене наведеним обсягом огляду.
