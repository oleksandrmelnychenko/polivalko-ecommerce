# Пошук на вітрині: розумний збіг і живі результати на сторінці

Погоджено з власником 2026-11-25 («Так, роби»).

## Навіщо

Покупець пише по-різному: множиною, з помилкою, російською, не на тій розкладці, додає зайві слова.
Пошук має все одно знаходити потрібне і ставити найвлучніше вгорі. Результати мають з'являтися на
основному екрані (сторінка `/search` з плитками й фільтрами) під час набору, а не у випадному віконці.

## Що було

- Збіг: кожне слово (після простого стемінгу) мусить бути в назві, бренді або slug (ILIKE). Інакше —
  триграмна схожість, позначена «схожі».
- Порядок результатів — сезонний (наявність, сезон, попит); від запиту залежить лише точний артикул.
- Розділ товару не враховується, тож «насіння томату» не знаходить «Томат … Seedera» (1648 таких товарів).
- Підказки — випадне віконце з 5 товарів у шапці.

## Підходи

1. **Розширити SQL (ILIKE/триграми) в EF.** Усе в базі, але оцінка релевантності й синоніми
   перетворюються на громіздкі динамічні вирази, а помилки в окремому слові погано ловляться.
2. **Текстовий індекс у пам'яті API (обрано).** Каталог малий (~5 тис. товарів, вибірка 1,3 мс). Для
   кожного запиту читаємо id, назви, бренд, slug, артикул, розділ; збіг і оцінку рахуємо в C#; у базу
   йде лише список id з порядком. Видимість, фільтри, фасети й ціни лишаються в SQL як були.
3. **Зовнішній пошуковий рушій (Meilisearch тощо).** Найкращі можливості, але нова служба в продакшні —
   надмірно для такого каталогу.

## Як працює збіг (бекенд)

- Слова запиту: нижній регістр, без розділових знаків; російські літери ы/э/ё/ъ → и/е/е/'.
  Стоп-слова («для», «на», «з», «і», «та», «в», «до», «по», «під», «від», «без») відкидаються.
- Кожне слово дає набір варіантів: основа (стемінг), синоніми й російські відповідники зі словника,
  транслітерація для slug.
- Слово збігається з товаром, якщо варіант є в назві/назві на вітрині, бренді, назві розділу
  (з батьківськими), slug (латиниця) або артикул починається з нього.
- Каскад: (1) усі слова; (2) якщо нічого і в запиті латиниця — те саме після перекладу розкладки
  EN→UA; (3) інакше слова, що не знайшли нічого, замінюються схожими (відстань редагування до слів
  каталогу) або відкидаються; результат позначається «схожі». Безглуздий запит → нічого, не «схожі».
- Релевантність (провідний ключ сортування, коли є запит і не вибрано сортування за ціною/назвою):
  точний артикул; збіг слів у назві (форма слова > початок довшого слова > частина) важить більше,
  ніж у розділі чи бренді. Далі — наявність; серед наявного спершу товар «про це слово» (слово стоїть
  до «для», «на», «з»…: «Шланг …» перед «Перехідник для шланга»), потім колишній сезонний порядок.
  Бонус «назва починається зі слова» над наявністю прибрано після перевірки на копії продакшну:
  він піднімав відсутні товари над тими, що є.

## Живі результати (вітрина)

- Віконце підказок прибрано. Набір у полі шапки через ~300 мс веде на `/search?q=…`: перший перехід
  з іншої сторінки — новий запис історії, далі — заміна. Enter працює як раніше.
- Поле не перемонтовується й не втрачає фокус під час набору; значення з URL підхоплюється лише при
  «Назад/Вперед».
- Зміна запиту скидає сторінку й фільтри. Порожній запит на `/search` показує підказку.

## Не робимо

- Пошук в описах і характеристиках (без індексу, ризик шуму).
- Нові поля у відповіді API (не чіпаємо OpenAPI/схему типів).

## Перевірка

Юніт-тести на нормалізацію, синоніми, розкладку, оцінку; інтеграційні тести API (старі сім лишаються
зеленими + нові). Якість — на копії продакшн-каталогу (`pv-prodcopy`) набором реальних запитів.
