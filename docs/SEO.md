# SEO вітрини

Заготовка зроблена за зразком gba_ecommerce (`docs/SEO.md`, `src/lib/seo/metadata.ts`) і пристосована до вітрини
Poli Valko: одна мова (українська), адреси без префікса локалі, дані магазину з консолі.

## Модуль `features/seo`

`web/apps/shop/src/features/seo` — фіча без залежностей; її використовують маршрути (`app/**`) і фічі `catalog`,
`product`, `content`, `services` (ребра в `apps/shop/eslint.config.mjs`).

| Файл | Що дає |
|---|---|
| `lib/site.ts` | `SITE_NAME` («Poli Valko»), `siteUrl()` з `SITE_URL`, `absoluteUrl(path)`, `organizationId()` і `websiteId()` (`…/#organization`, `…/#website`) |
| `lib/metadata.ts` | `seoMetadata({ title, description, path, images, noIndex, exactTitle })` — метадані сторінки: заголовок через `pageTitle` (« \| Poli Valko» один раз), опис, canonical, Open Graph (siteName, `uk_UA`, url, зображення), Twitter (`summary_large_image`, якщо є зображення, інакше `summary`), `noindex, follow` за потреби; `defaultOpenGraph` для кореневого layout |
| `lib/json-ld.ts` | генератори schema.org: `breadcrumbJsonLd`, `itemListJsonLd`, `webSiteJsonLd` (з SearchAction на `/search?q=`), `organizationJsonLd` і `contactPageJsonLd` |
| `lib/opening-hours.ts` | графік з консолі («Пн–Пт 9:00–18:00, Сб 10:00–15:00») → `OpeningHoursSpecification`; особливі дні → `specialOpeningHoursSpecification` (вихідний — `00:00–00:00`). Текст, який не розібрано, у розмітку не потрапляє |
| `components/json-ld.tsx` | `<JsonLd data={…} />` — `<script type="application/ld+json">`, `<` екранується як `<` |

## Що індексується

| Сторінки | Індексація | canonical |
|---|---|---|
| Головна, `/catalog`, `/services`, `/contacts`, `/payment-delivery`, `/returns`, `/offer`, `/privacy` | так | власна адреса |
| Розділ `/catalog/{slug}` | так | `/catalog/{slug}` |
| Сторінки розділу `?page=N` (лише цей параметр) | так, заголовок «Назва, сторінка N» | `/catalog/{slug}?page=N` |
| Розділ із фільтрами, сортуванням чи `pageSize` | `noindex, follow` | `/catalog/{slug}` |
| Товар `/product/{slug}` з фото, з ціною чи без, у наявності чи ні | так | `/product/{slug}` |
| Товар без фото | `noindex, follow`, поза sitemap; на сайті показується | `/product/{slug}` |
| «Акції» `/sale`, коли є акційні товари | так | `/sale` |
| «Акції» `/sale` без жодного акційного товару | `noindex, follow`, поза sitemap | `/sale` |
| Пошук `/search?q=…` | `noindex, follow` | — |
| Кошик, оформлення, кабінет, замовлення, оплата | `noindex, nofollow` | — |

Сторінка, що індексується, успадковує з кореневого layout `index, follow` і для Googlebot
`max-image-preview:large, max-snippet:-1, max-video-preview:-1`. Тому `seoMetadata` не задає ключ `robots`, коли
`noIndex` хибний: навіть `robots: undefined` затирає значення layout.

Пошуковикам пропонуємо товар, щойно він має фото; ні наявність, ні ціна не важать, тож сторінка не випадає з
індексу, коли товар розпродано чи чекає на ціну. Товар без фото показуємо на сайті, але не в пошуку, доки фото не
з'явиться (рішення власника від 26.11.2026). Товар із фото, але без ціни індексується без розмітки `Product`: вона
з'являється разом із ціною. Правило одне в двох місцях: API не віддає такий товар у sitemap (`GetSitemap.cs`), а вітрина
ставить на його сторінку `noindex, follow` (`isIndexableProduct` у `features/product`). Вітрина кешує sitemap на
години, а дані товару на хвилини, тому товар, який щойно втратив єдине фото, може недовго бути і в sitemap, і з
`noindex`; після оновлення кешу сигнали сходяться. Скрипт нижче перевіряє це на вибірці. Так само порожня сторінка
акцій: `saleIsEmpty` вирішує і про `noindex`, і про запис у sitemap; якщо каталог не відповів, індексація лишається
як була.

`lastmod` у sitemap ставимо лише з дати зміни, записаної в базі (`staticSitemapEntries`, `latestChange` у `features/seo`):
текстові сторінки з консолі (`/payment-delivery`, `/returns`, `/offer`, `/privacy`) беруть дату сторінки, сторінка
послуги — дату послуги, `/services` — найпізнішу з дат послуг. Розділ каталогу бере найпізнішу зміну серед власних
товарів і товарів усіх підрозділів (`GetSitemap.cs`); розділ без товарів — найпізнішу зміну в каталозі. Головна,
`/catalog`, `/contacts` і `/about` дати не мають: API не зберігає для них дати зміни, а вигадана дата привчає
пошуковик не зважати на це поле.

У типовому порядку списків («рекомендований» і «сезонний») спершу йде те, що можна купити, а серед нього й серед
решти — товари з фото (`SeasonalMerchandising`). Закріплені вручну товари й точність збігу в пошуку стоять вище.

Опис у розмітці `Product` — власний текст товару повністю (до 5 000 символів), без обрізання на 160-му символі;
`<meta name="description">` обрізається по межі слова.

## Товарний фід

`/feeds/google-merchant.xml` — фід для Google Merchant Center (безкоштовні товарні оголошення). RSS 2.0 з простором
імен `g:`; дані — `GET /api/v1/catalog/merchant-feed` (`GetMerchantFeed.cs`), XML складає `merchantFeedXml` у
`features/catalog`, маршрут — `app/feeds/google-merchant.xml/route.ts`. Дизайн:
`docs/superpowers/specs/2026-11-26-merchant-feed-design.md`.

- У фіді видимі товари з ціною понад нуль і хоча б одним фото; розпродані — з `out_of_stock`.
- `g:id` — артикул. Якщо артикул колись повториться, його лишає товар із меншим ідентифікатором, решта йдуть під
  власним ідентифікатором: так `g:id` не залежить від порядку.
- `g:gtin` — лише справжній штрихкод (та сама перевірка, що в розмітці товару); `g:mpn` — «Модель виробника».
  `g:identifier_exists` `no` — тільки для товару без бренду, GTIN і моделі.
- Зі старою ціною: `g:price` — стара, `g:sale_price` — поточна.
- Доставку налаштовують у самому Merchant Center; `google_product_category` Google визначає сам.
- Якщо API не відповів або повернув порожній список, маршрут відповідає 500: порожній файл з кодом 200 змусив би
  Merchant Center прибрати всі товари.

`Organization` у розмітці має `hasMerchantReturnPolicy`: Україна, 14 днів (зі сторінки «Повернення й обмін»).

## Службова адреса хостингу

Службова адреса хостингу `polivalko.vercel.app` віддавала весь магазин удруге. Тепер запит із цим хостом отримує 308
на ту саму адресу основного домену зі збереженням шляху й параметрів (`duplicateHostRedirects` у
`shared/lib/duplicate-hosts.ts`, підключено в `next.config.ts`). Правило потрапляє у збірку, лише коли задано
`SITE_URL`, і ніколи не перенаправляє основний домен на самого себе.

Пейджер списків (`pagerCells` у `features/catalog`) на кожному екрані показує першу, останню й поточну сторінку з
сусідами. На екранах від 72rem він додає ще двох сусідів і «круглий» стрибок на півдорозі до кожного краю; на вужчих
ці посилання лишаються в розмітці, приховані CSS. За посиланнями в розмітці будь-яка сторінка «Насіння» (70 сторінок)
лежить за 5 кліків від першої замість 35. Google рендерить сторінки з шириною телефона й приховані посилання може
важити менше, тож це ймовірний, а не виміряний виграш для обходу. Додаткові посилання мають `prefetch={false}`.

`robots.txt` закриває лише `/api/`, `/internal/` і сторінки з токеном в адресі (замовлення `/order/`, оплата
`/pay/`). Кошик, оформлення, кабінет, пошук і фільтри в ньому не закриті: роботу треба побачити їхній `noindex`,
інакше адреса, на яку є посилання, може потрапити в індекс без вмісту (порада з gba). Старі адреси товарів і розділів ведуть на нові одним 308-переходом
(перенаправлення з консолі, «Сайт → SEO → Перенаправлення»).

## Розмітка schema.org

| Сторінка | Типи |
|---|---|
| Головна | `Organization` + `Store` (назва, юридична назва й ІПН продавця, адреса, телефони, email, графік, особливі дні, мапа, соцмережі) і `WebSite` з пошуком |
| `/catalog` | `BreadcrumbList`, `ItemList` розділів |
| Розділ | `BreadcrumbList` (Головна → Каталог → батьківські розділи → розділ), `ItemList` товарів поточної сторінки |
| Товар | `Product` (`@id`, url, артикул, опис, фото, категорія, бренд, характеристики як `PropertyValue`) з `Offer` (ціна, валюта, наявність, `NewCondition`, продавець — організація магазину) і `BreadcrumbList` |
| Контакти | `@graph`: `Organization` + `ContactPage`; `BreadcrumbList` |
| Послуги, текстові сторінки | `BreadcrumbList` |

Дані організації беруться з API (`/api/v1/contacts`, `/api/v1/seller`), тобто з консолі: «Налаштування → Магазин»
(контакти, графік, особливі дні, соцмережі) і реквізити продавця. Порожнє поле в розмітку не потрапляє, вигаданих
значень немає.

## Звідки заголовки й описи

- Товари й розділи — `seoTitle` / `seoDescription` з API. Порожні сервер заповнює мета-шаблоном
  («Сайт → SEO → Мета-шаблони», змінні `{name}`, `{price}`, `{category}`, `{brand}`, `{shop}`); для товару без
  опису — перші 160 символів опису.
- Текстові сторінки — SEO-заголовок і опис сторінки з консолі («Сайт → Сторінки»), інакше заголовок і підзаголовок.
- Головна, каталог, контакти, послуги — тексти в маршрутах вітрини.
- Open Graph і Twitter повторюють заголовок з « | Poli Valko»; зображення — фото товару (до 4) чи розділу.

## Запуск у production

1. `SITE_URL` — публічна адреса з `https://` (з неї будуються canonical, `og:url`, sitemap, JSON-LD). Після зміни
   потрібна збірка `docker compose build web`.
2. Додати домен у Google Search Console. Для перевірки HTML-тегом задати `GSC_VERIFICATION` (у збірку вітрини
   потрапляє як `NEXT_PUBLIC_GSC_VERIFICATION`) і перезібрати `web`.
3. Подати `https://<домен>/sitemap.xml` у Search Console.
4. Перевірити кілька адрес у Search Console («Перевірка URL») і в Rich Results Test: головну, розділ, товар, контакти.
5. Прогнати скрипт перевірки (нижче) проти staging перед релізом.

## Перевірка

```bash
node tests/seo/check-seo.mjs
node tests/seo/check-seo.mjs --base=http://127.0.0.1:8081 --host=localhost:8081
node tests/seo/check-seo.mjs --base=https://www.poli-valko.com --thin=<slug товару поза sitemap>
```

Скрипт (Node 20+, без залежностей) бере розділ і товар із `sitemap.xml` (або `--category=`, `--product=`) і
перевіряє `robots.txt`, title, description, canonical, `og:title`/`og:url`, коректність JSON-LD і потрібні типи,
`noindex` на фільтрах, сортуванні, пошуку, кошику, оформленні й вході в кабінет. Також він перевіряє, що сторінки,
які індексуються, мають для Googlebot `max-image-preview:large`; що жодна з десяти товарних адрес, рівномірно
взятих зі sitemap (`--sample=N`), не має `noindex`; що `/sale` або є в sitemap й індексується, або відсутня там і
має `noindex`; а з `--thin=` — що товар поза sitemap має `noindex, follow`. Код виходу 1, якщо щось не пройшло.

## Що лишилось

- Зображення для соцмереж за замовчуванням (1200×630) і логотип для `Organization` — потрібні файли від магазину.
- Фото товарів у `sitemap.xml` — API sitemap віддає лише адреси й дати.
- `Offer` без `priceValidUntil` і доставки (`shippingDetails`) — додати, коли тарифи доставки будуть остаточні.
  Повернення вже є на рівні `Organization`.
