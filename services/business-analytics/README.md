# Бізнес-аналітика PoliValko

Розділ **Продажі → Бізнес-аналітика** у консолі читає звіт через staff API. Окремий Python-процес читає виробничий PostgreSQL в одній транзакції `REPEATABLE READ, READ ONLY`. Запити консолі працюють з останнім успішним знімком. Дата звірки та стан оновлення відображаються вгорі сторінки.

## Підключення на виробничому сервері

У Vercel приватний контейнер читає реквізити підключеної Production-інтеграції Neon. Він відкриває PostgreSQL-сесію через захищений WebSocket Neon на порту 443, перевіряє середовище, ідентифікатор проєкту, TLS і режим транзакції. Знімок для огляду та прогнозів кешується в пам’яті екземпляра. Редагування умов закупівлі доступне у варіанті з постійним томом.

Вкладка **Звірка накладних** окремим запитом читає реєстр і товарні рядки за обраний закритий рік. Графік показує видаткові накладні, касові чеки, повернення та чистий оборот. Чек із посиланням на проведену накладну враховується один раз. Кількість розбіжностей показує також документи, для яких різниці в загальній сумі взаємно погасилися. Замовлення сайту без відповідного облікового документа входять до ширшого огляду продажів.

Передайте сервісу секрет для окремого користувача з дозволами `CONNECT`, `USAGE` потрібних схем та `SELECT` таких таблиць.

| Схема | Таблиці |
|---|---|
| integration | dntrade_archive_records |
| accounting | references, documents, inventory_lines, inventory_reports, warehouse_stock, stock_movements, stock_openings, order_shipments |
| catalog | products, categories, product_stock |
| ordering | orders, order_items, order_refunds, order_refund_lines, order_status_changes |

| Змінна production Compose | Значення |
|---|---|
| `PRODUCTION_ANALYTICS_DSN_FILE` | Абсолютний шлях на сервері до файла з PostgreSQL URI або libpq conninfo. UID 10001 контейнера має мати право читання. |
| `PRODUCTION_ANALYTICS_HOST` | DNS-ім’я або IP виробничої БД, доступне з контейнера. Має збігатися з `host` у секреті. |
| `PRODUCTION_ANALYTICS_DATABASE` | Назва виробничої БД. Має збігатися з `dbname` у секреті. |
| `NOVAPOSHTA_SENDER_API_KEY` | Необов’язковий ключ кабінету відправника для звірки з реєстром ЕН. Поки ключ очікується, карта використовує адреси та документи з обліку. |

З’єднання з віддаленим сервером використовує TLS. Для приватного центру сертифікації змонтуйте кореневий сертифікат і задайте його шлях у контейнері через `sslrootcert` у секреті. Мережа `business-database` забезпечує вихід до виробничої БД. Сервіс доступний API через приватну мережу `business-console`.

Якщо БД працює у штатному контейнері PostgreSQL на виробничому сервері, вкажіть хост `production-analytics-postgres` у секреті й конфігурації. Цей псевдонім додає виробничий Compose-файл у приватній мережі. Для цього варіанта задайте `PRODUCTION_ANALYTICS_CLUSTER_ID` за результатом `SELECT system_identifier FROM pg_catalog.pg_control_system()` на відомому виробничому сервері та надайте аналітичній ролі право `EXECUTE` цієї функції. Сервіс перевіряє ідентифікатор до читання регістрів. У цій мережі для штатного PostgreSQL без TLS можна явно задати `sslmode=disable`.

До звичної **виробничої** команди Compose додайте третій файл. Нижче команда для сервера, на якому змінні наявного production-стека вже задані.

```sh
docker compose -f compose.yaml -f deploy/compose.production.yaml -f deploy/compose.business-analytics.yaml --profile app up -d --build business-analytics api console
```

Процес запускає звірку при старті та щодня о 02:15 за Києвом. Кнопка **Звірити з виробничою БД** запускає її позачергово. Повторний клік під час обчислення приєднується до поточного запуску. Повне перечитування враховує імпорт заднім числом, виправлення і видалення. Новий знімок публікується атомарно після успішного розрахунку. Знімок, стан останньої спроби та умови закупівлі зберігаються на серверному томі `business-analytics-data`. Цей том варто включити до резервного копіювання, щоб зберігати введені умови закупівлі.

## Зимові продажі та пропозиції

Вкладка **Зимові продажі** порівнює тижні з листопада до кінця лютого. Для групи з комплектом чек має містити категорію «Грунти та добавки» і хоча б одну з категорій «Горщики» або «Насіння». Обидві групи враховують повну суму покупки на касі чи за видатковою накладною. Наступні повернення у це порівняння середнього чека не входять. Для прибутку потрібна звірена сума рядків і собівартість кожної позиції. Оцінка заповнює пропуски маржею відповідного коду в агрегованому звіті DNTrade. Дата цього звіту та кількість охоплених покупок видимі поруч із результатом.

На вкладці **Пропозиції** менеджер вибирає контрагента й напрям, переглядає позиції з вільним залишком та ціною, задає кількість і реєструє виданий розрахунок. Можна також внести вже готову пропозицію. Міграція `20261121120000_SalesOffers` створює реєстр і зв’язки з накладними. Одна накладна належить одному розрахунку. Доступні кілька відвантажень за розрахунком. Для перегляду потрібні `analytics.products.view` та `accounting.registers.view`, для підготовки й реєстрації також `accounting.registers.edit`.

Для генерації через OpenAI задайте на сервері бізнес-аналітики `OPENAI_API_KEY` і `SALES_OFFER_MODEL` з назвою доступної текстової моделі Responses API зі Structured Outputs. Модель отримує назви й категорії відібраних товарів та агреговані ознаки покупок. Контактні дані, назва покупця, ціни та номери накладних залишаються в системі. За відсутності конфігурації або відповіді моделі менеджер бачить каталожну чернетку з позначеним джерелом. Для обмеженої ролі аналітики додатково надайте SELECT до `accounting.document_register`, `accounting.partners` і `catalog.product_prices`.

## Як читати результати

- Оборот дорівнює сумі товарних рядків продажів у гривнях за мінусом повернень. Пов’язані чек і накладна, а також позиції інтернет-замовлення і його відвантаження звіряються за документними посиланнями та кількістю. Склад без ідентифікатора відображається окремо. Реєстр показує розбіжність між сумою товарних рядків і сумою всього документа.
- Валовий прибуток охоплює рядки з документованою собівартістю або відновлюваною середньозваженою вартістю складського руху. Для складської оцінки потрібен підтверджений порожній початковий залишок і неперервна послідовність кількостей з оціненими надходженнями. Для пов’язаного повернення використовується встановлена собівартість первісного продажу. Частка покриття обчислюється за сумою продажів та повернень до згортання.
- Тижневий прогноз SKU має горизонт 4 тижні, прогноз категорії на складі — 13. Для категорій окремо розраховуються продажі у гривнях до повернень та кількість у сумісних відомих одиницях. Для прогалин використовується ознака наявності документів складу в тижні. Це ознака активності, а повноту самого імпорту потрібно звірити з джерелом. Для SKU враховуються задокументовані інтервали нульового залишку. Залишок на кінець дня відновлюється з початкового залишку та всіх змін кількості за датами документів, тому кілька продажів за день і проведення заднім числом не спотворюють інтервал. Якщо відновлений облік не сходиться з поточним залишком складу, інтервал визначається за залишками, збереженими після кожного руху.
- Для тижневого попиту сервіс порівнює середні за 4 і 8 тижнів, відповідні тижні торік, ті самі тижні з поправкою на річну зміну продажів, модель частоти та розміру нерегулярних продажів і навчену лінійну регресію з регуляризацією. Учасники проходять однакові послідовні перевірки, включно з періодами нульових продажів. Для SKU до перевірок за останні пів року додаються ті самі тижні попередніх років, якщо історії вистачає для навчання кожної моделі. Перед сезоном модель обирається за тим, як вона працювала в цьому сезоні, а не в тихі місяці перед ним. Коли історії близько двох років, у тому самому сезоні перевіряються лише простіші моделі. Останній період відкладено для незалежної перевірки WAPE та зміщення. Межі побудовано за 80-м процентилем абсолютних помилок попередніх перевірок. Для сезонної моделі це помилки в ті самі тижні попередніх років.
- Тижні без залишку і тижні без документів складу є невідомими, а не нульовими. Коли невідомі останні тижні, прогноз спирається на останні відомі продажі в межах 20 тижнів, а в рядку видно тривалість перерви. За довшої перерви прогноз не будується.
- Разове велике замовлення торік не переноситься в прогноз. Тиждень, що втричі перевищує 90-й процентиль тижнів із продажами і не повторювався в ті самі тижні роком раніше, замінюється рівнем сусідніх тижнів. Якщо попередній рік недоступний, значення лишається без змін.
- Вкладка **Прогноз обороту** показує очікуваний чистий оборот у гривнях на 3, 6 або 12 місяців після останнього завершеного місяця з даними. Джерелом є заголовки документів із виробничої звірки та чеки без проведеної накладної. Місячні агрегати кешуються в пам’яті на 15 хвилин. Для навчання використовується неперервна історія до 10 років. Прогалини та документи без підтвердженої суми переривають ряд. Сервіс порівнює недавнє середнє, торішній місяць і сезонну регресію за однаковими історичними стартами. Вкладка показує прогноз і факт на окремому відкладеному періоді та емпіричні межі за кожним кроком, для якого накопичено щонайменше п’ять помилок.
- Умови закупівлі задаються для організації, складу та SKU. Це строк поставки, період між закупівлями й страховий запас у днях. Внесіть дати та кількості підтверджених надходжень або підтвердьте порожній список. Сервіс віднімає резерви, розподіляє прогноз рівномірно по днях і визначає найбільший дефіцит у періоді покриття після строку поставки. Окремо показується перший день вичерпання запасу. Надходження після дати дефіциту не усуває попереднього браку. Рекомендований обсяг не створює закупівельного документа.

Для перегляду і запуску звірки потрібен дозвіл `analytics.products.view`, для деталізації документів додатково `accounting.registers.view`, для редагування умов закупівлі — `accounting.registers.edit`.

Серед місячних моделей також є прогноз із поправкою на зміну обороту між роками. На кожному історичному старті він оцінює множник за останніми доступними парами однойменних місяців і застосовує його до торішнього сезонного профілю. Він бере участь у тих самих перевірках, що й решта моделей.

## Перевірка прогнозу на власній історії

Тижневий прогноз можна перевірити на вже опублікованому знімку продажів. Команда не звертається до бази даних і нічого не записує.

```sh
docker compose -f compose.yaml -f deploy/compose.production.yaml -f deploy/compose.business-analytics.yaml exec business-analytics python -m analytics.backtest
```

Для 300 найпродаваніших SKU прогноз на 4 тижні будується з кожної четвертої точки останнього року лише за попередніми продажами і порівнюється з фактом. Таблиця за місяцями показує зміщення та WAPE прогнозу і, для порівняння, середнього за 8 тижнів. Від’ємне зміщення означає прогноз, нижчий за факт. Параметри `--weeks` і `--series` змінюють глибину перевірки та кількість товарів, `--series 0` бере всі. У варіанті на Vercel збереженого знімка немає, тому команда там недоступна.

Нову версію сервісу можна перевірити ще до перемикання. Зберіть образ і запустіть його без мережі з томом сервісу лише для читання. Назву тому показує `docker volume ls`. Команді потрібні тільки дата звірки, продажі та інтервали без залишку, тому вона читає і знімок попередньої версії.

```sh
docker compose -f compose.yaml -f deploy/compose.production.yaml -f deploy/compose.business-analytics.yaml build business-analytics
docker run --rm --network none -v <проєкт>_business-analytics-data:/var/lib/business-analytics:ro --entrypoint python polivalko-business-analytics:${APP_VERSION:-latest} -m analytics.backtest
```

Після оновлення сервіс не використовує знімок попередньої версії прогнозу. До завершення першої звірки розділ показує стан очікування.

## Перевірка першого виробничого звіту

Вкладка **Контрагенти й карта** показує покупки та повернення за картками покупців, чистий оборот і дату останньої покупки. Для географії можна вибрати доставку за документами, адресу з картки контрагента або доставку вебзамовлень за довідником Нової пошти. Вибір області відкриває її карту з кругами над населеними пунктами. Площа круга пропорційна кількості покупок або додатній сумі за рік. Таблиця включає також повернення і від’ємний оборот. Для кожного джерела видно покупки з невідомою областю, а в межах області — покупки без підтвердженого населеного пункту.

Режим «Доставка або адреса покупця» зараховує продаж один раз. Сервіс шукає відправлення в архівних замовленнях DNTrade та у відвантажених поштових замовленнях магазину. Для зв’язку використовує ТТН, номер замовлення або посилання на батьківське замовлення. Рік визначає дата документа продажу. Номери архівних замовлень звіряються в межах облікового запису, а суперечливі збіги відкидаються. Якщо підтвердженої області доставки немає, карта використовує адресу з картки покупця. Окремий лічильник показує, скільки покупок у вибраному регіоні вдалося нанести на карту саме за відправленнями.

Населені пункти визначаються всередині Python-сервісу за кодом КАТОТТГ або за однозначною назвою з урахуванням області й типу. Межі областей і географічні центри населених пунктів проєктуються в одну систему координат. Відтворити файли карти з відкритих джерел можна командою `python services/business-analytics/build_market_geography.py katottg.csv geoBoundaries-UKR-ADM1_simplified.geojson`. [Вхідний довідник ua-geo](https://raw.githubusercontent.com/alexbabintsev/ua-geo/d37d5e967e3bb45255d180ea740e5a6ca90e00cc/data/out/katottg.csv) · [Вхідні межі geoBoundaries](https://media.githubusercontent.com/media/wmgeolab/geoBoundaries/9469f09/releaseData/gbOpen/UKR/ADM1/geoBoundaries-UKR-ADM1_simplified.geojson)

Після першої звірки виберіть закритий рік і склад. Порівняйте чистий оборот та повернення з реєстром обліку й відкрийте документ із розбіжністю. Для одного SKU перевірте первісний продаж, повернення, покриту собівартість та одиницю виміру. Для перевірки закупівель зіставте доступний залишок, резерви, дату найближчої поставки і рекомендований обсяг із даними закупівельника.
